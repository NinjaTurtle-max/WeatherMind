## 관측 01 · 1라운드 통합 진단
**백엔드 전 범위 격차 요약**

WeatherMind는 7주 해커톤 MVP, 듀오링고는 DAU 수천만의 12년 된 프로덕션이다. 격차는 우열이 아니라 구조적 선택의 차이로 읽어야 하며, 이 규모에서 배울 것과 무시할 것을 가려내는 것이 목적이다. 상태는 세 단계로 표기한다 — **동급 이상**(이 규모 기준 견고함), **얇음**(개념은 있으나 방어·확장 장치 부재), **부재**(축 자체가 없음).

## 관측 02 · 중점 심층 분석
**콘텐츠 플레이 다양성 — 가장 큰 격차는 여기에 있다**

1라운드 진단에서 게이미피케이션·인프라 격차를 다뤘지만, 사용자가 실제로 체감하는 격차의 근원은 "오늘 앱을 열었을 때 할 수 있는 플레이의 종류와 양"이다. 이 축에서 두 서비스의 거리가 가장 멀다.

### 2.1 듀오링고의 플레이 인벤토리 — 5계층 구조
듀오링고의 콘텐츠는 단일 "문제 풀기"가 아니라 다섯 계층의 포맷 포트폴리오다. 각 계층은 서로 다른 사용 맥락(짧은 틈새 시간·긴 몰입·수동적 소비)을 담당한다.

| 계층 | 포맷 | 구성 | 담당하는 맥락 |
| :--- | :--- | :--- | :--- |
| **코어 연습** | 레슨 (10~15문항, 2~5분) | 번역 단어은행 · 탭 페어 매칭 · 듣고 쓰기 · 말하기(음성인식) · 빈칸 채우기 · 문장 배열 · 그림-단어 매칭 등 10종 이상의 문항 유형을 한 세션에 믹스 | 일일 핵심 루프 |
| **서사형** | Stories · Adventures | 인터랙티브 대화·미니 시나리오, 중간중간 이해도 체크 삽입 | 긴 몰입, 맥락 학습 |
| **수동 소비형**| DuoRadio | 팟캐스트형 듣기 + 가벼운 체크 — 손이 바쁠 때도 스트릭 유지 가능 | 저에너지 시간대 |
| **대화형 AI** | Video Call(Lily) · Roleplay | LLM 실시간 회화, 발화 자체가 플레이 | 고급 학습자, 프리미엄 |
| **세션 변형** | 타임어택 · Legendary · 실수 복습 | 같은 문항 뱅크를 시간압박·고난도·복습 규칙으로 재포장 | 반복 플레이 동기 |

구조 면에서는 코스 → 섹션 → 유닛 → 레슨의 트리에 선행관계가 걸려 있고, 유닛 리뷰·체크포인트가 중간 평가를 담당한다. 중요한 것은 **다섯 계층이 전부 하나의 문항 뱅크와 하나의 세션 생성기 위에서 돌아간다는 점이다** — 포맷은 포장이고, 백엔드 자산은 공유된다.

### 2.2 WeatherMind의 현재 플레이 표면
| 모듈 | 플레이 | 빈도 · 분량 | 상태 |
| :--- | :--- | :--- | :--- |
| **오늘의 퀴즈** | 객관식 · 단답 · 슬라이더 3유형 중 1문항 + RAG 피드백 | 1문항 / 일 | 구현 |
| **기후 시뮬레이터** | 파라미터 조작 → 클라이언트 계산 (채점·보상 없음) | 자유 | 축소판 |
| **기상 리그** | 주간 예측 제출 → 월요일 정산 | 1회 / 주 | 구현 |
| **기후 탐정** | 사건 해결형 (서사형 계층에 해당) | — | 미구현 |

### 2.3 격차의 6개 축
1.  **세션이라는 개념 자체가 없다.** 듀오링고의 원자 단위는 "레슨"(문항 10~15개 묶음)이지만 WeatherMind의 원자 단위는 "문항 1개"다. quiz_logs는 단건 행이고 세션 테이블이 없다. 하루 1문항이면 체류 시간 약 1분 — 스트릭은 있는데 오늘 더 할 것이 없다.
2.  **문항 유형 3종 vs 10종+.** 더 중요한 건 모달리티다: WeatherMind는 전부 텍스트 읽고 답하기이고, 듣기·말하기·조작·이미지 판독이 없다. 날씨는 본질적으로 시각(위성·레이더·그래프) 도메인이라 이 부재가 더 아깝다.
3.  **포맷 계층이 1개뿐.** 코어 연습만 있고 서사형(탐정 — 미구현), 수동 소비형, 대화형 AI, 세션 변형이 없다. 사용 맥락 다변화가 안 된다.
4.  **커리큘럼 그래프 부재.** concept_tag 6종이 평면 태그로만 존재한다. 선행관계·유닛·진도 개념이 없어 "다음에 뭘 배우지"를 시스템이 답할 수 없고, 학습이 누적되는 느낌(진도 바, 유닛 완료)을 줄 수 없다.
5.  **세션 생성 엔진 부재.** 듀오링고 백엔드의 심장은 session generator다 — 신규/복습 배합, 난이도 곡선(쉬움→어려움→쉬움 마무리), 유형 다양성 보장을 서버가 결정한다. WeatherMind의 Router Chain은 "오늘 1문항의 태그"만 고른다. 방향은 같은데 결정의 단위가 다르다.
6.  **반복 플레이 동기 부재.** 문항을 다 풀어도(1개니까 즉시) 타임어택·복습 모드·고난도 재도전 같은 재포장 플레이가 없다. XP를 더 벌 방법이 없으니 리그·레벨 시스템도 공회전한다.

> **핵심 판단**
> 이 6개 축은 전부 하나의 부재로 환원된다: **문항 뱅크 + 세션 모델이 없다는 것.** 플레이 유형 10종을 먼저 만드는 게 아니라, 뱅크와 세션이라는 기반 자산을 먼저 깔면 유형·포맷·변형은 그 위의 포장 문제가 된다. 이것이 §4 설계의 출발점이다.

### 2.4 백엔드 함의
*   **채점기의 플러그인화** — 현재 `_grade()`는 quiz 라우터 안의 단일 함수다. 유형이 늘면 question_type별 채점기 레지스트리(매칭·배열·이미지 선택은 각각 채점 규칙이 다름)로 분리해야 한다.
*   **미디어 자산 파이프라인** — 이미지 판독(위성·레이더)은 KMA 이미지 API 프록시·캐시가, 듣기 도입 시 TTS 생성·저장이 필요하다.
*   **문항 통계** — 유형별 정답률·소요 시간 집계가 세션 엔진의 입력이 된다. 지금은 문항이 1회성이라 통계가 쌓일 곳이 없다(§1의 route 미저장 문제와 같은 뿌리).

## 관측 03 · 벤치마킹의 경계
**무엇을 가져올 수 있고, 무엇은 새로 만들어야 하는가**

저작권은 표현(expression)을 보호하고 아이디어·메커니즘은 보호하지 않는다. 스트릭·리그·XP·하트 같은 게임 메커니즘은 업계 전반이 공유하는 설계 어휘이며, 듀오링고 자신도 선행 게임들에서 가져왔다. 반면 그 메커니즘을 감싼 표현물 — 캐릭터, 이름, 그래픽, 사운드, 문항 텍스트 — 은 저작권·상표로 보호된다. 경계선을 표로 못 박는다.

| 구분 | 항목 | 판단 |
| :--- | :--- | :--- |
| **차용 가능**<br>(메커니즘 · 아이디어) | 스트릭 + 프리즈, XP·레벨, 리그 승강제, 코호트 매칭, 퀘스트, 하트/에너지 | 게임 메커니즘 — 저작권 비보호 영역 |
| | 레슨 = 문항 묶음, 세션 생성, 신규/복습 배합, 난이도 곡선 | 교수 설계 방법론 — 자유롭게 벤치마킹 |
| | 문항 유형의 "종류"(매칭, 배열, 빈칸, 듣기 등) | 퀴즈 형식 자체는 보호 대상 아님 |
| | 간격 반복, 지식 추적, ML 알림 최적화 등 공개 논문의 기법 | 공개 연구 — 단, 특허 존재 여부는 상용화 전 별도 확인 |
| **자체 제작 필수**<br>(표현 · 식별자) | 부엉이 Duo 등 캐릭터·일러스트·애니메이션 | 저작권 + 상표 — 유사 캐릭터(초록 새 계열)도 회피 |
| | "Duolingo", "Duo", "Super Duolingo", "Birdbrain" 등 네이밍·로고 | 상표 — 마케팅 문구의 "듀오링고풍/날씨판 듀오링고" 표기도 금지 |
| | 문항·스토리·캐릭터 대사 등 콘텐츠 텍스트 | 저작물 — WeatherMind는 KMA 데이터 + 자체 생성이므로 이미 충족 |
| | 효과음·음원, UI 그래픽 에셋, 앱스토어 스크린샷 구도 | 저작물 — 전부 자체 제작 |
| | 화면 전체의 종합적 look & feel을 그대로 재현하는 것 | 트레이드 드레스 — 출처 혼동을 일으키면 부정경쟁 리스크 |

**실무 원칙 4가지**
1.  **메커니즘은 도메인으로 번역해서 가져온다.** 그대로 이식이 아니라 "날씨라서 이렇게 된다"로 변형하는 것이 법적으로도 안전하고 제품으로도 강하다(§4의 플레이 설계가 이 원칙의 실행).
2.  **식별 요소는 전부 독자 세계관으로.** 마스코트·네이밍·비주얼은 기상 도메인 고유의 것으로 새로 만든다. 티어 이름도 Bronze→Diamond를 베끼지 않고 구름 분류 체계를 쓴다(§4.5).
3.  **비교 언급은 내부 문서까지만.** 대외 발표·스토어 설명에서 타사명을 끌어와 포지셔닝하지 않는다.
4.  **콘텐츠 출처를 스스로 증명 가능하게.** 문항 뱅크에 생성 근거(KMA 데이터·자체 시드 문서)를 기록해 두면 콘텐츠 저작권 분쟁에서 방어 자료가 된다 — §4.1의 뱅크 스키마에 `source` 필드로 반영.

> **면책**: 본 절은 공개된 일반 원칙의 정리이며 법률 자문이 아니다. 상용 출시·투자 유치 단계에서는 특허(간격 반복·알림 최적화 관련 출원 여부 포함) 검토를 전문가에게 받는 것을 전제로 한다.

## 관측 04 · 설계
**날씨 네이티브 학습 게임으로의 구체화**

설계 원칙은 하나다: **듀오링고의 뼈대(뱅크 → 세션 → 포맷 계층)를 가져오되, 살은 전부 날씨 도메인 고유의 것으로 채운다.** 특히 WeatherMind만의 무기 — **오늘의 실제 하늘이 교재가 된다** — 를 모든 계층에 관통시킨다. 이것은 정적 콘텐츠 기반인 듀오링고가 구조적으로 흉내낼 수 없는 축이다.

### 4.1 콘텐츠 아키텍처 — 하이브리드 문항 뱅크
현재의 "매 요청 LLM 생성"과 듀오링고의 "전량 사전 검수"를 절충한다. 문항 템플릿은 검수된 정적 자산으로 뱅크에 축적하고, 오늘의 실황 데이터는 슬롯으로 주입한다. 재현성(문항 통계·IRT 추정 가능)과 실시간성(오늘 날씨 반영)을 동시에 얻고, LLM의 역할은 온라인 생성에서 뱅크 저작 보조 + 폴백으로 이동한다.

*   **품질 게이트**: 생성 직후 별도 체인이 ① 정답 유일성 ② 보기 중복·모호성 ③ 근거 문서 일치를 검증하고, 통과분만 `draft` 상태로 뱅크에 적재 → 관리자 승인 시 `active`. 운영 중에는 문항별 정답률 이상치(전원 정답 95%+ 또는 10%-)와 사용자 신고로 자동 `retired` 처리.
*   **실황 슬롯**: 템플릿에 `{today.temp_max}`, `{today.sky}` 같은 변수를 두고 서빙 시점에 Redis의 `weather:{date}:{region}` 캐시로 치환. "오늘 서울이 흐린 이유는?" 유형이 매일 새 문항처럼 소비되지만 통계는 템플릿 단위로 쌓인다.
*   **폴백 체계**: 뱅크 미스 → 온라인 생성(현행 경로) → 그것도 실패 시 공용 캐시 문항. 현재 503으로 끝나는 경로에 강등 단계가 하나 늘어난다.

### 4.2 커리큘럼 구조 — 평면 태그에서 트리로
`concept_tag` 6종을 유지하되 그 위에 섹션/유닛 계층을 얹는다. 기존 태그는 유닛의 속성이 되므로 `weak_tags`·Router Chain과 하위 호환된다.

| 섹션 | 유닛 예시 | 연결 태그 | 대응 학령 |
| :--- | :--- | :--- | :--- |
| **S1 하늘 읽기** | 기온과 하루 · 구름의 종류 · 비가 오는 이유 | `air_mass` | elementary |
| **S2 공기의 힘** | 고기압과 저기압 · 전선의 충돌 · 바람의 방향 | `pressure_front` | middle_high |
| **S3 큰 바람** | 태풍의 일생 · 태풍 진로 읽기 | `typhoon` | middle_high |
| **S4 도시와 기후** | 열섬 · 탄소와 기온 · 이상기상 사례 | `heat_island` · `co2_climate` · `anomaly` | middle_high · adult |

유닛마다 레슨 3~5개 + 유닛 리뷰 1개. 진도는 `user_progress(user_id, unit_id, crowns)`로 기록하고, 선행관계는 유닛 테이블의 `prereq_unit_id` 하나로 시작한다(그래프 DB 불필요).

### 4.3 플레이 타입 10종 — 듀오링고 대응과 날씨 네이티브 변형
전부 §4.1의 뱅크와 §4.4의 세션 엔진 위에서 돌아가는 "포장"이다.

| 고유 유형 | TIER | 설명 | 대응 벤치마크 및 백엔드 요구사항 |
| :--- | :--- | :--- | :--- |
| **개념 페어 매칭** | 1 | "저기압 ↔ 상승기류 ↔ 구름 생성" 개념-현상 짝 맞추기. 탭 페어의 날씨판. | 탭 페어 매칭 · 백엔드 match 채점기 |
| **인과 사슬 배열** | 1 | "일사 → 지면 가열 → 상승기류 → 적운"처럼 기상 현상의 인과 순서를 배열. | 문장 배열 · 백엔드 ordering 채점기 |
| **실황 판독** | 1 | 오늘 실측 데이터를 근거로 "지금 하늘이 이런 이유" 고르기. | 현행 객관식 유지 · 백엔드 슬롯 치환 |

| **그래프 판독** | 2 | 기온·습도 시계열 그래프에서 특이점 짚기. 데이터 리터러시. | 고유 유형 · 백엔드 시계열 데이터 번들링 |

| **기후 탐정** | 3 | 이상기상 사건을 단서 카드로 추리하는 스토리형. | Stories · 백엔드 분기 시나리오 모델 |
| **AI 기상캐스터 롤플레이**| 3 | AI 앵커 역과 실황 데이터로 예보 방송 리허설. RAG 체인 재활용. | Video Call · 백엔드 대화 상태 관리 |

세션 변형 계층은 별도 유형 없이 규칙만 얹는다: **스피드 관측**(타임어택 — `elapsed_sec` 활용), **오답 노트**(weak_tags 하위 복습 세션), **완벽한 예보**(무오답 클리어 시 배지 — Legendary 대응).

### 4.4 세션 엔진 — Router Chain의 승격
Router Chain의 결정 단위를 "오늘 1문항의 태그"에서 "오늘 세션의 구성"으로 올린다. 배합 규칙은 서버 구성값으로 두어 하드코딩 문제를 함께 해소한다.

```python
# 일일 세션 기본 배합 (5~7문항, 원격 구성으로 조정 가능)
session_recipe = {
  "new":      2,  # 현재 유닛 진도의 신규 문항
  "review":   2,  # weak_tags accuracy<60 태그 우선 복습
  "live":     1,  # 오늘의 실황 슬롯 문항 (WeatherMind 고유)
  "speed":    1,  # 타임어택 1문항 (콤보 XP)
}
# 난이도 곡선: easy → hard → easy 마무리 (정서적 종결감)
# 유형 다양성 제약: 같은 question_type 연속 2회 초과 금지
```

### 4.5 게이미피케이션 확장 — 날씨 세계관으로 독자화
메커니즘은 벤치마킹하되 명칭·상징은 전부 기상 어휘로 새로 만든다.

*   **리그 개편**: 층운(시작) → 적운(ELO 1100+) → 난층운(1250+) → 적란운(1400+) → 태풍의 눈(상위 1%). 구름 분류 체계를 써서 교육 서비스 정체성 부합. 코호트 매칭은 유저 확보 시점까지 유보.
*   **스트릭 방어**: "구름 방패" (users.streak_freeze_count 추가).
*   **퀘스트/배지**: "오늘 XP 30", "실황 문항 풀기" 등 일일 퀘스트 도입.
*   **마스코트(제안)**: 저기압이 다가오면 낮게 나는 습성으로 예로부터 날씨의 전령이었던 **제비 계열 캐릭터** — 과학적 근거가 있는 상징이면서 듀오링고 부엉이와 시각적으로 분리된다.

### 4.6 학습 경로의 시각 기하 — 크롬 실측 대조 (2026-08-13)

클라이언트 지시 *"학습 경로가 형태는 좋은데 부자연스러워 · 경로는 크롬으로 선행 학습 앱 경로 디자인을 봐"*에 따라 **크롬에서 읽기 전용으로 직접 실측**했다.

> ⚠️ **관측 조건**: 브라우저에 기존 세션이 살아 있어 경로 본화면이 그대로 열렸다. 관측자는 **로그인·회원가입을 하지 않았고 자격증명을 입력하지 않았다**. 공개 범위 밖을 우회한 것이 아니라 사용자 브라우저의 기존 상태다.
> ⚠️ 이 절은 앱 이름 표기가 **허용된 두 곳 중 하나**다(`CLAUDE.md` 어휘 규약). 코드 주석·커밋에서는 「선행 학습 앱」으로 쓰고 **이 절을 경로로 참조**한다.

| 항목 | 듀오링고(실측) | 우리(종전) | 판정 후 |
|---|---|---|---|
| 노드 지름 **70px** | 70px | 32px | **64px** |
| 세로 피치 | 76·86·98·89·77 → 평균 **85.2px** | 54px | **86px** |
| 노드당 가로 이동 | ±25~45px | ±74px | ±45px |
| 가로 총 폭 | 140px | 208px | 128px |
| **진폭/피치** | **0.82** | **1.93** | **0.744** |
| 최대 각도(수직 기준) | 28° | 54° | 28° |
| **연결선** | **그리지 않음** | 10px 리본 | **제거** |

**해석 — 「부자연스러움」의 정체는 두 가지였다.**

1.  **길이 옆으로 눕는다.** 진폭/피치가 1.93이라 한 칸 내려가는 동안 참고 앱보다 **2.4배 더 옆으로** 움직였다. 참고 앱의 길은 압도적으로 수직이고 좌우 흔들림은 곁들임이다.
2.  **연결선의 존재 자체.** 참고 앱은 길을 **아예 그리지 않는다** — 진도는 노드 상태(완료·현재·잠금)가 나른다. 여섯 항목 중 시각적으로 가장 큰 차이였다.

**부수 관측**: 노드가 커서(70px) 아이콘 판독성이 높다. 우리 32px에서는 아이콘이 17.6px이라 상태 구분이 한계였고, 64px에서 35px이 된다.

**소유권**: 위 수치는 `frontend/src/modules/curriculum/PcCurriculumPath.jsx`의 `PATH_*` 상수가 구현을 소유하고, `frontend/tests/learnPath.smoke.test.mjs`가 **이 표에서 값을 파싱해** 대조한다(리터럴 중복 금지 — 관찰이 갱신되면 기대값이 따라 움직인다).

## 관측 05 · 사례 연구
**듀오링고 체스 — 세션 엔진이 "상태형 도메인"을 삼킨 사건**

2025년 듀오링고는 체스 코스를 출시했다. 이 사례가 결정적인 이유는 체스가 최초의 **상태형(stateful) 시뮬레이션 도메인**이기 때문이다. "보기 고르기"가 아니라 살아있는 보드를 조작하는 것. 날씨 시뮬레이터가 가야 할 길이다.

### 5.1 코스 구조
*   **이론 레슨**: 규칙 해설(Oscar 코치) + 보드 위 짧은 연습.
*   **퍼즐 (75%)**: "2수 만에 체크메이트" 등 정답이 존재하는 제약 상황. 짧은 루프.
*   **미니 매치 (90초)**: 90초 내 기물 1~2개만 사용해 포획 미션. 제약+압박 재미.
*   **풀 매치 (25%)**: 대국. 서사적 승부.

### 5.2 시사점 & WeatherMind 매핑
*   **보드가 곧 문항이다**: 4지선다가 아니라 대기 보드(시뮬레이터)에서의 조작 자체가 답안이 되어야 한다.
*   **75:25 법칙**: 샌드박스만 열어두면 재미가 없다. 목표와 제약(기물/변수 제한)을 둔 '상황 퍼즐'이 75%를 차지해야 한다.

| 체스 코스 | WEATHERMIND 대응물 | 기존 자산 연결 |
| :--- | :--- | :--- |
| 체스판 (상태 보드) | **대기 보드** — 시뮬레이터를 문항 표면으로 승격 | 기후 시뮬레이터 (클라이언트 계산) |
| 전술 퍼즐 (75%) | **상황 퍼즐** — 초기 대기 상태 + 목표 달성 | content_items 뱅크 |
| 미니 매치 (90초) | **미니 미션** — 변수 1~2개 · 90초 제한 | elapsed_sec 수집 인프라 |
| 풀 매치 vs Oscar | **예보 대결** — AI 기상캐스터와 예보 승부 | 리그 ELO · KMA 실측 정산 |
| Oscar (상대/코치) | **마스코트 캐릭터** (제비 등) | R4 롤플레이 통합 |

> **체스에는 없는 WeatherMind의 패**
> 체스 정답은 엔진이 계산하지만, **날씨의 승패(예보 대결)는 내일 실제 하늘이 정산한다.** 현실이 정산하는 구조의 몰입감과, 실제 과거 기상 이변(anomaly_cases)을 초기 조건으로 쓰는 '실화 기반 퍼즐'은 어떤 보드게임도 주지 못하는 묘미다.

## 관측 06 · 재미의 설계
**문항이 게임이 되는 조건 — 시뮬레이션 콘텐츠의 재미 설계**

### 6.1 재미 4분면 진단
*   **Hard fun(도전)**: 상황 퍼즐, 미니 미션, 별점 재도전 추가
*   **Easy fun(탐색)**: 대기 보드의 토이 루프 (조작 즉시 하늘이 변함)
*   **Serious fun(성취)**: ELO 성장 그래프, 재현 퍼즐("실제 태풍 사건을 풀었다")
*   **People fun(관계)**: AI 캐스터 캐릭터와의 매일 예보 대결

### 6.2 재미 설계 5원칙
1.  **조작 결과의 즉각적 가시화**: 물리적 정확도보다 인과 관계 피드백 속도가 우선.
2.  **제약이 재미를 만든다**: 모든 파라미터를 여는 대신 습도 1개만 조작하도록 잠가야 미션이 됨.
3.  **실패는 정보다**: 하트 차감 대신 힌트(개념 카드 → 조작 방향) 제공 및 별점 차감 방식(교육 최적화).
4.  **유일 정답이 아닌 목표 상태를 채점한다**: "서울에 비"가 목표라면 어떤 경로로든 비를 내리면 정답 인정.
5.  **짧은 루프 속에 숙련 곡선**: 90초~3분 길이로 세션 엔진 배합에 녹여냄.

## 관측 07 · 실행 계획
**로드맵 — R2에서 R4까지**

### R2 — 기반 자산과 부채 상환
*   **목표**: "하루 1문항"을 "하루 1세션"으로. 실기동 전 부채 상환.
*   문항 뱅크(`content_items`) + 품질 게이트 체인 + 실황 슬롯 주입.
*   세션 엔진(`session_recipe` 배합) + 라우터 및 로깅 보완.
*   스트릭 방패 추가, 경로 레이트리밋(비용 방어) 구현.

### R3 — 플레이 다양화와 보상 루프 완성
*   **목표**: 세션이 매일 달라 보이게. XP 획득/소비 사이클 완성.
*   Tier 1 신규 유형 3종 추가 및 채점기 레지스트리 패턴 적용.
*   대기 보드 퍼즐 도입 (클라이언트 시뮬 코어 추출 및 서버 목표 검증).
*   유닛 진도 구조(`user_progress`) 적용.
*   구름 티어(리그 승강제), 퀘스트, 배지 기능 추가.

### R4 — 확장 계층과 리텐션 인프라
*   **목표**: 포맷 포트폴리오 다변화. 사용 맥락 다변화.
*   Tier 2/3 유형 (이미지 위성 판독, 기후 탐정, 롤플레이) 오픈.
*   **예보 대결**: AI 마스코트와 매일 저녁 예보 승부.
*   푸시 리마인더(Celery Beat 활용), 문항 통계가 쌓인 시점에서 IRT 모델 활성화.

> **한 줄 방향성**
> 듀오링고에서 가져올 것은 부엉이가 아니라 "뱅크 위의 세션, 세션 위의 포맷"이라는 뼈대다. 체스 코스가 증명했듯 그 뼈대는 상태형 보드(시뮬레이터)까지 훌륭히 소화한다. 거기에 "오늘의 하늘이 교재이자 심판"이라는 듀오링고가 갖지 못한 차별점을 관통시키는 것이 WeatherMind의 독자적 자리다.
