# 스프린트 R10-07 — 문항 유형별 페이로드 노출 (P0 선재 결함)

> **로드맵 위치**: 마일스톤이 아니라 **결함 수정 트랙**. R10-01 S6의 실서버 구동에서
> 발견됐다(2026-08-03). 전략 SSOT: `docs/ROADMAP.md`.
> **발견 경로**: 실서버 UI를 처음 끝까지 걸어보다 유닛 세션의 match 문항에서
> **연결할 항목이 하나도 렌더되지 않는 것**을 사용자가 발견. 풀 방법 없이 제출되어
> 자동 오답 + 구름 −1까지 발생했다.

## 0. 결함 — 무엇이 왜 깨졌나

`SessionItem`은 문항 페이로드를 **두 통로**로만 내보낸다: `options`(객관식용 컬럼)과
`template_json`. 그런데 `routers/session.py:72`의 `_board_template_json()`은
**board 유형일 때만** 화이트리스트 필드를 반환하고 **나머지 유형은 `None`**이다
(`schemas/session.py:19-22` 주석이 그 의도를 명시한다 — "board 유형만 … board 외
유형은 None").

결과: `match`의 `pairs`, `ordering`의 `items`가 **API 응답에 존재하지 않는다.**
프론트는 `question.pairs ?? question.template_json?.pairs ?? []`로 읽으므로 `[]`가 되어
**항목 0개로 렌더**된다.

### 실측 영향 (2026-08-03, 실서버 확인)

| 유형 | 프론트 요구 필드 | 시드 보유 | API 노출 | 실서버 상태 | 문항 수 |
|---|---|---|---|---|---|
| multiple_choice | `options` | ✓ | ✓(전용 컬럼) | 정상 | 21 |
| short_answer | — | — | — | 정상 | 7 |
| **cloze** | — (`question_text`의 `___`) | ✓ | ✓ | **정상** | 3 |
| board | `template_json` 전체 | ✓ | ✓(화이트리스트) | 정상 | 12 |
| **match** | `pairs` | ✓ | **✗ None** | **🔴 풀 수 없음** | **3** |
| **ordering** | `items`·`shuffled` | ✓ | **✗ None** | **🔴 풀 수 없음** | **3** |
| **slider** | `min`·`max`·`step`·`unit` | **✗ 시드에 없음** | ✗ | ⚠️ 기본값 0~100으로 렌더 | 4 |

- **못 푸는 문항 6개**(match 3 + ordering 3) = 시드 53문항의 **11%가 사용 불가**.
- slider 4문항은 **동작은 하지만** 단위 표시가 없고 범위가 문항 의도와 무관하다
  (정답 17 m/s·25 ℃·50 %·7 %를 0~100 슬라이더에서 맞춘다). 시드 저작도 필요하다.
- **유닛 세션도 같은 직렬화**를 쓴다(`curriculum.py:95` → `session_today_response`)
  → **수정 지점은 한 곳**이고 데일리·유닛이 함께 해결된다.

### 왜 아무 테스트도 못 잡았나 (같은 실수의 3번째 반복)

R10-01의 보드 진입 게이트 P1과 **구조가 동일**하다 — 계약·mock·테스트가 전부 초록인데
실사용 경로가 끊겨 있었다.

1. **mock은 손으로 쓴 픽스처**라 `pairs`·`items`를 다 갖고 있다 → 프론트 스모크 전건 통과.
2. **백엔드 테스트는 FakeDB·순수 함수**라 "API가 그 필드를 실제로 노출하는가"를 보지 않는다.
3. `test_session_board_item.py`의 화이트리스트 계약은 **board만** 감시한다.
4. QA 스모크는 왕복 **상태 코드**만 봤고 **유형별 풀이 가능성**은 보지 않았다.

→ **mock↔서버 드리프트를 유형 단위로 검증하는 가드가 없다.** 이것이 이 스프린트의
진짜 산출물이다(수정 자체는 작다).

**R10 회귀가 아니다.** `_board_template_json`은 R3에서 board용으로 도입됐고
match·ordering은 그때부터 노출된 적이 없다. R10이 만든 게 아니라 **R10이 드러냈다** —
실서버 UI를 처음 제대로 걸어봤기 때문이다. 관찰 보고서 §1-3의 *"match 유형: 짝 성립 시
목록 재배열"* 지적조차 **mock에서만 가능한 관찰**이었다.

## 2. 계약 (고정)

### 2.1 유형별 페이로드 화이트리스트 (S1)

`_board_template_json`을 **유형별 화이트리스트**로 일반화한다. 이름도 실체에 맞게 바꾼다
(예: `_question_payload`).

| 유형 | 노출 키 |
|---|---|
| board | 현행 유지 — `mode`·`guide_steps`·`initial_state`·`palette`·`goal_conditions`·`hints`·`question_text`·`time_limit_sec` |
| **match** | `pairs` |
| **ordering** | `items` · `shuffled` |
| **slider** | `min` · `max` · `step` · `unit` |
| multiple_choice · short_answer · cloze | `None`(현행 유지 — 추가 페이로드 불필요) |

- **`correct_answer`는 어떤 유형에서도 절대 노출하지 않는다.** 현행 board 화이트리스트의
  방어 의도를 전 유형으로 승계한다. `explanation_hint`도 제외(정답 유도).
- 노출 통로는 **기존 `template_json` 필드를 재사용**한다 — 스키마에 새 필드를 만들지
  않는다(프론트가 이미 `question.template_json?.pairs` 폴백을 갖고 있어 무수정으로 붙는다).
- **키가 시드에 없으면 그 키를 넣지 않는다**(빈 값·기본값 주입 금지 — 데이터 부재가
  가려지면 S4를 영원히 못 찾는다).

### 2.2 유형 전수 계약 가드 (S2) — 이 스프린트의 핵심

**시드의 모든 문항을 대상으로**, 프론트 컴포넌트가 요구하는 필드가 API 응답에 존재하는지
검증한다. 유형이 늘거나 프론트 요구가 바뀌면 즉시 실패해야 한다.

- 요구 필드 표는 **테스트 안에 명시**한다(`match→pairs`, `ordering→items` 등).
- **7유형 전수**를 돈다 — 시드에 있는 유형이 하나라도 빠지면 실패.
- `correct_answer`·`explanation_hint`가 **어떤 유형에서도 응답에 없음**을 함께 고정.
- **공허 통과 방지**: 시드에서 해당 유형이 0건이면 실패(가드가 조용히 무력화되는 경로 차단).

### 2.3 mock↔서버 정합 계약 (S3)

R10-01에서 드러난 드리프트 3건을 계약으로 묶는다.

| 항목 | 계약 |
|---|---|
| 세션 문항 수 | mock 세션 items 수 == `SESSION_RECIPE` 총합(5). **현재 mock은 9로 위반** |
| 보드 퍼즐 수 | mock `BOARD_PUZZLES` 수 == 시드 board 문항 수(12). **현재 mock은 4로 위반** |
| 유형별 필드 | mock이 내보내는 유형별 필드 집합 ⊇ 서버가 내보내는 집합 |

> **주의**: mock 수치 교정은 관찰 보고서에 영향을 준다 — §1의 *"첫날 세션 **9문항** 중
> 4개 중복"*의 분모 9가 mock 값이었다(실서버는 5). 중복 결함 자체는 실재했고 D2로
> 수정됐으나, **규모 서술이 실제보다 커 보였고 그 수치가 R10-B를 P0로 올린 근거였다.**
> 보고서에 단서를 남긴다.

### 2.4 slider 시드 저작 (S4)

4문항에 `min`·`max`·`step`·`unit`을 저작한다. 정답이 범위 중앙 부근에 오도록 하고
단위를 명시한다(예: 태풍 기준 → `min:0 max:40 step:1 unit:"m/s"`, 정답 17).
**추측으로 범위를 정하지 말고 문항 의도(질문 문구)에 맞춰라.**
