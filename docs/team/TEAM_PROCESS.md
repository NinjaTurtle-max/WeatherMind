> 에듀테크(듀오링고형 데이터 주도 조직)·게임·일반 SW 개발사의 공개된 실무 관행
> (Scrum Guide, Google Engineering Practices, DORA 리서치, 각사 엔지니어링 블로그)을
> 조사·종합한 뒤, 이 프로젝트 규모(서브에이전트 7직군·인원 변동, 1주 스프린트)에 맞게

## 1. 직군별 실무 프로세스 조사 요약과 본 프로젝트 적용

### 1.1 PM (Product Manager)
- **실무 관행**: 에듀테크 선두 조직은 "가설 → 실험 → 지표 검증" 루프로 움직인다(듀오링고의
  A/B 문화가 대표). PM은 백로그의 단일 소유자로서 PRD·유저 스토리(INVEST 원칙)·
  수용 기준(Acceptance Criteria)을 작성하고, 우선순위는 RICE/MoSCoW로 정하며,
  스프린트 목표와 완료 정의(DoD)를 관리한다. 게임사에서는 여기에 "재미 검증
  플레이테스트" 게이트가 추가된다.
- **본 프로젝트 적용**: 오케스트레이터(메인 에이전트)가 PM을 겸한다. 산출물 —
  스프린트 백로그, 서비스 간 계약 고정, 웨이브 종료 시 리뷰 노트, 관측 보고서 갱신.

### 1.2 백엔드 엔지니어
- **실무 관행**: API 계약 우선(contract-first) — 구현 전에 엔드포인트·스키마를 고정해
  프론트와 병렬 작업을 가능하게 한다. DB 마이그레이션은 반드시 리뷰 대상이며 롤백
  가능해야 한다. 테스트 피라미드(단위 > 통합 > E2E), 트렁크 기반 + 작은 PR,
  구조적 결정은 ADR(Architecture Decision Record)로 남긴다.
- **본 프로젝트 적용**: backend/ 소유. 계약은 스프린트 문서 §3에 고정. 신규 로직은
  pytest 단위 테스트 동반. 마이그레이션은 기존 0001과 충돌 없는 0002로 증분.

### 1.3 프론트엔드 엔지니어
- **실무 관행**: 컴포넌트 주도 개발(CDD) — 화면이 아니라 상태를 먼저 정의한다
  (로딩/빈/오류/성공). API mock을 계약 기반으로 먼저 만들어 백엔드와 병렬로 진행.
  디자인 토큰·상태관리 규율(스토어는 도메인별 최소), 접근성 기본 체크.
- **본 프로젝트 적용**: frontend/ 소유. mock/apiMockPlugin.js를 계약과 동기화한 뒤
  UI 작업 — 백엔드 완성 전에도 전체 플로우가 mock으로 동작해야 한다.

### 1.4 AI 엔지니어
- **실무 관행**: 프롬프트는 코드와 동일하게 버전 관리하고 변경 이유를 기록한다.
  골든셋(평가용 고정 입력·기대 출력) 기반 회귀 평가로 프롬프트 수정의 퇴행을 잡는다.
  출력은 반드시 스키마 검증(가드레일)을 거치고, LLM 불가용 시의 결정적(deterministic)
  폴백을 함께 설계한다. 비용·지연 예산을 기능 단위로 관리한다.
- **본 프로젝트 적용**: ai-worker/ 소유. 신규 체인은 ① LLM 없이도 동작하는 휴리스틱
  1차 검증 ② LLM 2차 검증의 2단 구조로, API 키 부재 환경에서도 테스트 가능해야 한다.

### 1.5 데이터 엔지니어/애널리스트
- **실무 관행**: 데이터 계약(data contract) — 이벤트·콘텐츠의 스키마를 생산자·소비자가
  합의한 문서로 고정한다. 콘텐츠 데이터는 품질 규칙(유일성·커버리지·금칙어)을 체크리스트로
  강제한다. 지표는 지표 정의서(metric dictionary)로 이름·수식·집계 기준을 통일한다.
- **본 프로젝트 적용**: database/seed/ + docs/data/ 소유. 문항 시드는 계약 스키마
  (스프린트 문서 §3.3)를 준수하고, 저작 가이드를 문서 자산으로 남긴다.

### 1.6 QA 엔지니어
- **실무 관행**: 시프트 레프트 — 구현 완료를 기다리지 않고 계약 단계에서 테스트 케이스를
  설계한다. 리스크 기반 우선순위(돈·데이터 손실 > 핵심 루프 > 표시 오류), 버그는
  P0(차단)~P3(사소) 심각도로 분류. 게임 QA는 기능 테스트에 더해 밸런스·재미
  플레이테스트를 별도 트랙으로 운영한다.
- **본 프로젝트 적용**: backend/tests/ + docs/qa/ 소유(웨이브 2 투입). 계약 기반
  테스트 + 게이미피케이션 수치(07번 공식) 검증 + 통합 체크리스트 실행.

### 1.7 DevOps 엔지니어
- **실무 관행**: 모든 인프라는 코드로(IaC), CI는 lint → test → build 순의 파이프라인,
  환경 패리티(로컬=운영 구성 최소 차이), 시크릿은 코드 밖으로. DORA 4지표(배포 빈도·
  리드타임·변경 실패율·복구 시간)가 팀 건강의 표준 척도다.
- **본 프로젝트 적용**: 루트 인프라 파일 + scripts/ 소유(웨이브 2 투입). git 저장소·
  로컬 CI 스크립트(lint+test+compose config)·런북 정비.

## 2. 팀 공통 운영 규칙

### 2.1 애자일 운영 (축약형 스크럼)
- **스프린트 1주** 단위. 흐름: 백로그 작성(PM) → 계약 고정 → 웨이브 병렬 개발 →
  코드 리뷰 → 통합 검증(QA) → 리뷰 노트·회고 기록.
- 세리머니는 비동기 문서로 대체: 스탠드업 = 각 에이전트의 완료 보고,
  회고 = 스프린트 문서 하단 "회고" 섹션.
- 스토리는 수용 기준(AC)을 포함해야 하며, AC 미달 산출물은 DoD 미충족으로 반려.

### 2.2 완료 정의 (DoD)
1. 스프린트 문서의 계약(§3)과 산출물이 일치한다.
2. 신규 로직에 단위 테스트가 있고 통과한다 (`pytest`).
3. 다른 직군 소유 디렉토리를 수정하지 않았다.
4. 결정 사항이 문서(모듈 docstring 또는 docs/adr/)에 남아 있다.
5. 코드 리뷰 지적 사항이 반영되었다.

### 2.3 코드 리뷰 규칙
- 모든 변경은 커밋 전 리뷰를 거친다. 리뷰 관점 우선순위:
  **정확성(계산·채점·마이그레이션) > 계약 일치 > 테스트 충분성 > 가독성·중복**.
- 리뷰어는 PM(오케스트레이터)이 겸하고, 웨이브 종료 시 전체 diff에 대해
  코드 리뷰를 수행 → 지적 사항을 해당 직군 에이전트가 수정 후 커밋.
- 커밋은 웨이브 단위, 메시지에 직군 스코프를 표기한다 (예: `backend: 세션 API 추가`).

### 2.4 Git 브랜치·PR 워크플로우 (R5.5~ 적용)
- **배경**: R2~R5.5는 트렁크 기반(전부 `main` 직접 커밋)으로 진행했다 — 병렬 검토할
  실제 2번째 리뷰어가 없어 계약 선고정(§2.1)이 PR의 대체 장치였다. 이제부터는
  `/code-review`를 실질적 게이트로 세워 브랜치·PR 방식(1.2 백엔드 실무 관행 "트렁크
  기반 + 작은 PR")을 실제로 적용한다. **과거 커밋은 재편하지 않는다** — 새 작업부터.
- **브랜치 네이밍**: `<type>/<scope>-<slug>` — type은 `feat`·`fix`·`chore`·`docs` 중
  하나, scope는 스프린트·항목 코드(예: `r6-01`, `r5.5-5`). 예: `feat/r6-01-detective-story`.
- **작업 흐름**:
  1. `main`에서 새 브랜치 생성 (`git checkout -b <branch>`).
  2. 기존 관례대로 항목 단위 원자적 커밋(예: R5.5-1~4 패턴 유지) — 웨이브 끝에
     한 번에 몰아서 커밋하지 않는다.
  3. PR 열기 전 브랜치 전체 diff에 **`/code-review` 실행** — P0~P2 지적 사항을
     전부 반영 후 재검토까지 마친다(DoD 2.2-5와 동일 기준).
  4. `gh pr create`로 PR 오픈 (Summary·Test plan 포함).
  5. 병합은 **Merge commit**(squash 금지) — 항목별 원자 커밋 이력을 보존한다.
  6. 병합 후 브랜치 삭제(`gh pr merge --delete-branch`).
- **리뷰어**: 실제 2인 검토가 없는 구조이므로 `/code-review`(및 보안 관련 변경 시
  `/security-review`)의 통과가 "PM(오케스트레이터) 리뷰"를 대체한다 — §2.3의
  리뷰 관점 우선순위(정확성 > 계약 일치 > 테스트 충분성 > 가독성·중복)를 그대로 적용.
- **GitHub 브랜치 보호(선택)**: 강제하려면 `main`에 "require PR before merge"를
  걸 수 있으나, 1인 저장소에서 되돌리기 번거로운 리포 설정 변경이라 사용자가
  명시적으로 요청할 때만 적용한다 — 기본은 프로세스 규율로만 강제.

### 2.5 문서화 자산화 정책
- **SSOT 계층**: docs/specs/(제품 스펙) > docs/DEVELOPMENT_PLAN.md(표준 결정) >
  docs/team/(운영·스프린트) > 코드 docstring.
- **ADR**: 구조적 선택(스키마 설계, 라이브러리 채택 등)은 docs/adr/NNN-제목.md
  (배경/결정/대안/결과 4절)로 기록한다.
- 스프린트 백로그·리뷰 노트는 삭제하지 않고 누적한다 — 다음 라운드의 컨텍스트 자산.
- 벤치마킹 분석은 관측 보고서(아티팩트)로 관리하며 큰 결정 변경 시 갱신한다.

### 2.6 동적 팀 편성 — 개발량 기반 인원 조절 (R10~ 적용)
- **원칙**: 직군(§1의 7개)은 고정이나 **인원은 고정이 아니다**. 백로그 확정 직후
  PM(오케스트레이터)이 직군별 개발량을 산정해 인원을 배정하고, 스프린트 도중에도
  재산정한다 — 개발량 0인 직군은 아예 투입하지 않는다(R10에서 데이터/AI 미투입).
- **개발량 산정 지표** (항목별로 합산):
  1. 신규·수정 파일 수와 그 파일들의 **소유 분할 가능성**
  2. 계약 표면 크기 (엔드포인트·스키마·컴포넌트 prop 인터페이스 개수)
  3. 신규 테스트 수 (계약 테스트 + 단위)
  4. 미확정 설계 리스크 (웨이브 0에서 확정해야 할 인터페이스 개수)
- **인원 배정 규칙**:
  - **1인 = 원자 커밋 3~6개 / 소유 파일 6개 내외**가 기준선. 이를 넘으면 증원 검토.
  - **파일 소유를 배타적으로 쪼갤 수 없으면 증원하지 않는다** — 분할 가능성이 인원
    상한이다. DoD 2.2-3(타 직군 디렉토리 불가침)을 직군 *내부*에도 그대로 적용한다.
  - 2인 이상 병렬이면 **격리 등급을 §2.6.1로 판정**한다(인원 수가 아니라 **계약 성숙도**가
    기준이다 — R10 웨이브 1에서 "2인 이상=격리"라는 인원 기준을 세워놨는데도 지켜지지
    않았고, 그 원인이 기준이 애매해서였다).
  - **동시 상한 5** — 리뷰·통합 대역폭이 병목이므로 그 이상은 웨이브를 쪼갠다.
- **조절 시점**: ① 백로그 확정 직후 초기 배정 ② **웨이브 0 종료 시 재산정**(계약이
  확정되며 실제 개발량이 드러남) ③ 웨이브 중 블로킹·범위 변동 발생 시 증원/감원.
- 배정 결과와 변경 이유는 해당 스프린트 문서 §4(웨이브)에 남긴다 — 회고 자산.

#### 2.6.1 워크트리 격리 — 방법과 비용 (사고 2026-08-01 이후 필수)

**왜 파일 소유 분리로 부족한가**: 소유 분리는 **편집 충돌**을 막지만, `git stash`·
`reset`·`checkout`·`clean`은 파일 단위가 아니라 **워킹트리+인덱스 전체**에 작용한다.
2026-08-01 웨이브 1에서 한 담당이 자기 베이스라인 측정용으로 `git stash -u
--keep-index`를 실행해 **5인 작업분이 전부 되돌아갔다**(백업으로 복구, 손실 0).
소유 분리만으로는 **git 명령의 폭발 반경**을 막을 수 없다.

**방법**: 에이전트를 띄울 때 워크트리 격리 옵션을 준다(각자 독립 워킹트리+인덱스,
`.git` 객체는 공유). 수동이면 `git worktree add .claude/worktrees/<담당> -b <브랜치>`.

**브랜치만 나누는 것은 해결이 아니라 악화다.** 하나의 워킹트리에는 체크아웃된 브랜치가
정확히 하나(HEAD 1개)다. 공유 트리에서 담당별로 `git checkout -b`를 하게 하면 **전원의
HEAD가 마지막 사람 것으로 바뀐다** — stash 사고와 같은 종류이면서 더 자주 터진다.
**워크트리가 곧 "N개 브랜치를 동시에 체크아웃"하는 장치**이고, git은 같은 브랜치를 두
워크트리에 체크아웃하는 것을 거부하므로 워크트리를 쓰면 **브랜치 분리가 자동 강제**된다.

#### 판정 기준 — 인원 수가 아니라 **계약 성숙도**

격리는 안전을 주고 **가시성을 뺏는다.** 이 교환비가 유리한지는 계약이 고정됐는지로
갈린다. 인원 수로 판정하지 마라.

| 등급 | 조건 | 구성 | 파괴적 git |
|---|---|---|---|
| **T0** 공유 | 1인 | 메인 트리 | 금지 |
| **T1 공유+소유분리** | 2인 이상이고 **계약을 아직 발견 중**(웨이브 0 성격: 탐색·계약 선고정·경계 추출) | 메인 트리 + 배타적 파일 소유 목록 | **금지** |
| **T2 완전 격리** | 2인 이상이고 **계약이 고정됨**(웨이브 1 성격: 구현) | 담당별 워크트리 + 브랜치 | 금지 |

- **T1을 택하는 이유**: 탐색 단계에서는 서로의 발견이 즉시 보이는 게 이득이다. R10 웨이브 0에서
  FE-2가 `PeninsulaMap` 추출 중 좌표계 결합을 찾아내 계약 자체를 바꿨다 — 격리됐으면 병합까지
  몰랐다.
- **T2를 택하는 이유**: 계약이 고정되면 서로를 볼 필요가 없다. 웨이브 0이 존재하는 이유가
  정확히 **T2를 안전하게 만드는 것**이다(mock 선반영·계약 테스트·파일 소유 확정).
- **격리가 뺏는 것을 인정하라**: 웨이브 1에서 FE-3이 SA-1의 `clouds_spent` 착지를 같은
  트리에서 보고 즉시 배선했고, FE-1이 FE-2의 정적 import가 메인 번들에 25 kB 얹은 것을
  발견해 알렸다. T2에서는 둘 다 병합 시점까지 묻힌다 → **아래 "발견 공유" 규약으로 보전**.

#### T2 브랜치 계층과 통합 순서

```
main
└─ <type>/<스프린트>-w<N>-integration      ← 웨이브 통합 브랜치 (PM 단독 소유)
   ├─ <type>/<스프린트>-w<N>-sa1-<slug>    ← .claude/worktrees/sa1
   ├─ <type>/<스프린트>-w<N>-fe1-<slug>    ← .claude/worktrees/fe1
   └─ …
```
1. PM이 통합 브랜치를 `main`에서 딴다. 담당 브랜치는 **통합 브랜치에서** 딴다(main 아님 —
   웨이브 0 산출물을 상속해야 한다).
2. 담당은 자기 워크트리에서만 작업하고 **커밋하지 않는다**(§2.7 그대로 — 커밋은 PM).
3. PM이 담당별로 **실제 테스트 출력·diff 검증 → 원자 커밋 → 통합 브랜치로 병합**. 검증
   실패분은 **그 브랜치만 버린다**(공유 트리에서는 커밋을 골라내야 했다 — 이게 T2의 실익).
4. 웨이브 종료 시 통합 브랜치 → `main` **PR 1건**(§2.4 유지, merge commit).
5. 병합 후 워크트리·브랜치 정리: `git worktree remove <경로>` → `git branch -d <브랜치>`.

#### T2 착수 체크리스트 (프론트는 3종 세트 필수 — 실측 근거)

| 항목 | 백엔드 | 프론트 |
|---|---|---|
| 워크트리 + 브랜치 | 필요 | 필요 |
| **`node_modules` 심링크** | 불필요 | **필수** |
| **dev 서버 포트 배정** | 불필요 | **필수** |

실측(2026-08-03, 빈 워크트리에서 직접 확인):
- 백엔드는 준비 0으로 `python -m pytest tests -q` → `853 passed`. 전역 파이썬 환경을 쓰므로
  저장소 파일만 있으면 된다.
- 프론트는 `npm run build` → **`sh: vite: command not found`**. 워크트리는 git 추적 파일만
  담고 `node_modules/`는 `.gitignore` 대상이라 존재하지 않는다(119MB).
  심링크 후 재실행 → `✓ built in 2.21s`.
  ```
  ln -s <메인>/frontend/node_modules <워크트리>/frontend/node_modules
  ```
  `node_modules/`는 gitignore라 링크가 git에 보이지 않는다. **다만 심링크는 의존성을 공유
  한다** — 어떤 담당이 새 의존성을 추가해야 하면 그 담당만 자기 워크트리에 실제
  `npm install`을 하게 하고(링크 해제), 브리핑에 명시한다.
- **포트는 격리 대상이 아니다.** 웨이브 1에서 FE 3인이 5199·5210·5231을 각자 띄우며 서로의
  HMR을 깨뜨려 FE-2는 검증 화면 진입이 반복 실패했다. 브리핑에 담당별 포트를 지정한다.

#### 격리해도 유지할 규약 4건

1. **파괴적 git 금지(담당)** — `stash`·`reset`·`checkout`/`restore`로 변경 버리기·`clean`·
   `add`·`commit`. 격리는 남의 작업을 지키지만 **자기 워크트리는 여전히 망칠 수 있다.**
   검증이 필요하면 읽기 전용 대안을 쓴다: `git show HEAD:<path>`로 원본 확인,
   `git diff`로 비교, 임시 하네스는 `/tmp`에.

2. **PM도 예외가 아니다 — 담당이 도는 트리에서 브랜치를 바꾸지 않는다.**
   1번은 담당에게만 걸려 있었고 **PM 자신은 예외로 두는 공백**이 있었다. 실제로 터졌다:
   **2026-08-03 PM이 S6를 병합하려고 담당이 작업 중인 공유 트리에서 `git checkout main`을
   실행**해 그 담당이 수정해야 할 계약 테스트 2개와 소스 수정이 트리에서 걷혔다(미커밋
   변경이 0인 순간이라 **운으로 손실 0**이었을 뿐이다). PM의 브랜치 전환은 담당의
   `git stash`와 **같은 폭발 반경**을 갖는다.
   - **PM이 담당 실행 중에 하면 안 되는 것**: `checkout`/`switch`(브랜치 전환)·`merge`·
     `pull`·`rebase`·`reset`·`stash`. 트리의 HEAD와 파일을 바꾸는 모든 것.
   - **PM이 해도 되는 것**: `add`·`commit`(검증한 산출물 커밋은 PM의 일이다)·`push`
     (트리 무변경)·`status`·`diff`·`show`·`log`.
   - **병합·PR은 담당이 전부 끝난 뒤**에 한다. 급하면 **별도 워크트리/클론에서** 병합하고
     담당이 도는 트리는 건드리지 않는다.
   - 실수로 바꿨다면: **즉시 원래 브랜치로 복귀**하고, 담당에게 **트리가 흔들렸다는 사실과
     "지금 시점에서 대상 파일을 다시 읽어라"를 통보**한다(구버전을 읽고 작업했을 수 있다).
   - 이 규약이 T2 격리의 또 다른 이유다 — 담당이 자기 워크트리에 있으면 PM의 전환이
     담당을 건드리지 못한다.
3. **발견 공유** — 자기 소유 밖에서 발견한 문제는 고치지 말고 **PM에게 보고**한다(파일:줄
   근거 포함). PM이 소유자에게 전달한다. T2가 뺏는 우연한 상호 발견을 이 채널로 보전한다.
   R10 실례: FE-1의 번들 지적 → PM이 FE-2에게 전달 → 메인 번들 11.33 kB 감소.
   - **자기 파일에서 찾은 버그도, 같은 패턴이 다른 파일에 있으면 보고 대상이다.**
     "소유 밖에서 발견한 것"만 보고하면 이 경우가 빠진다 — 고쳐놓고 자기 버그 수정으로만
     보고하면 **같은 결함이 남의 파일에서 계속 산다.**
     R10 실례: FE-2가 지도 오버레이의 `dispose()`가 `loseContext()`로 컨텍스트를 죽여
     StrictMode 재마운트에서 셰이더 컴파일이 실패하는 버그를 찾아 고쳤으나 **자기 버그
     수정으로만 보고**했다. 같은 코드가 FE-1의 단면 렌더러에 그대로 있었고, 그 결과
     **WebGL 단면 1,528줄이 실브라우저에서 통째로 SVG로 폴백**됐다 — 테스트는 전부
     초록이었고, PM이 실서버를 직접 구동할 때까지 아무도 몰랐다.
   - 판단 기준: 수정한 버그가 **"이 파일만의 실수"가 아니라 "패턴·관례의 실수"**라면
     보고한다. 공유 프리미티브(GL 컨텍스트 생명주기·이벤트 정리·좌표 변환·상태 초기화)
     주변이면 대개 후자다.
4. **공유 파일은 단일 소유자** — 여러 담당이 필요한 파일(예: `frontend/mock/apiMockPlugin.js`)은
   한 명에게 배타 소유를 주고 나머지는 **읽기 전용**으로 둔다. 변경이 필요하면 소유자를
   경유한다(R10 D5). 격리해도 이 규칙은 필요하다 — 병합 시 충돌하기 때문이다.

**비용으로 인정할 것**: 워크트리 N개 = 브랜치 N개 = **병합 N회**. 파일 소유가 갈려
있으면 대개 충돌 없이 병합되지만 통합 단계가 하나 늘어난다 — 이 비용을 감수하는
것이 5인 작업분을 한 번에 날리는 위험보다 싸다.

### 2.7 중첩 오케스트레이션 — 서브에이전트 내부 파생
- **구조**: 한 직군 인원이 2 이상이면 그 직군의 **리드** 1인을 세우고, 리드가 자기
  직군 범위 안에서 작업을 쪼개 **자기 세션 내에서 워커를 파생**한다. 오케스트레이터는
  직군 리드만 상대하므로 팬아웃 폭이 늘어도 PM의 컨텍스트가 터지지 않는다.
- **깊이 상한 2** — 오케스트레이터 → 직군 리드 → 워커. **워커는 더 파생하지 않는다**
  (파일 소유 추적 불능 + 리뷰 대역 초과). 3단 이상이 필요하면 스프린트를 쪼갠다.
- **파생 계약** (리드가 워커를 띄울 때 프롬프트에 반드시 포함):
  1. **배타적 소유 파일 목록** — 형제 워커와 한 파일도 겹치지 않게
  2. 먼저 읽을 계약 문서 경로 (스프린트 문서 §3, `board_rules.json` 등)
  3. 수용 기준(AC)과 실행할 테스트 명령
  4. 금지 범위 — 타 직군 디렉토리, 공용 설정 파일, 계약 파일 자체의 수정
  5. 반환 형식 — 변경 파일 목록 + 테스트 결과(요약이 아니라 실제 출력)
- **런타임 제약 폴백**: 서브에이전트가 추가 파생을 할 수 없는 환경·에이전트 타입이면,
  리드는 **분할 계획만 반환**하고 오케스트레이터가 같은 파생 계약으로 대신 팬아웃한다
  — 계약 내용과 소유 분할은 동일하게 유지한다.
- **통합 순서**: 리드가 자기 직군 산출물을 먼저 통합하고 직군 단위 회귀를 돌린 뒤
  오케스트레이터에 보고 → 오케스트레이터가 웨이브 통합(§2.1)을 수행한다.
- **리뷰 권한은 위임 불가**: `/code-review` 게이트(§2.4-3)는 브랜치 단위로
  오케스트레이터가 직접 실행한다. 리드의 자체 검토는 이를 대체하지 않는다.
- **에이전트 보고는 무비판 수용 금지**: 워커·리드의 "완료" 보고는 테스트 실제 출력과
  diff로 확인한 뒤에만 DoD 충족으로 인정한다.
